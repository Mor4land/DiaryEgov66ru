# Документация ботов MirageDiary (Telegram & MAX)

Техническое руководство по архитектуре, криптографической защите данных, роутингу команд, подсистемам напоминаний и эксплуатации ботов платформы MirageDiary.

## 1. Обзор архитектуры и стек технологий

Боты MirageDiary для Telegram и MAX (Мессенджер ВКонтакте / MAX Messenger) функционируют как единая экосистема поверх общего ядра и сервисного слоя ASP.NET Core:

```
[ Telegram App ]       [ MAX Messenger ]       [ WebApp / MiniApp ]
       │                       │                        │
       ▼                       ▼                        ▼
[ Telegram Bot API ]   [ MAX Webhooks/REST ]   [ Reverse Proxy (Nginx) ]
       │                       │                        │
       └───────────────┬───────┴────────────────────────┘
                       ▼
         ┌───────────────────────────┐
         │   MirageDiary.Server      │
         │   (.NET 10 / Kestrel)     │
         └─────────────┬─────────────┘
                       │
       ┌───────────────┼──────────────────────────────┐
       ▼               ▼                              ▼
┌──────────────┐ ┌───────────────┐        ┌───────────────────────┐
│ MirageDiary. │ │ SQLite 3      │        │ Внешние сервисы:      │
│ Core         │ │ (app.db 0600) │        │ • dnevnik.egov66.ru   │
│ • PKCE S256  │ │ • enc:v2: DEK │        │ • ЕСИА (Госуслуги)    │
│ • DiaryClient│ │ • 152-ФЗ logs │        │ • Russian Trusted CAs │
└──────────────┘ └───────────────┘        └───────────────────────┘
```

### Технологический стек
* **Среда выполнения**: .NET 10 (C# 14), режим компиляции Release, сборка под `linux-x64`.
* **Telegram Bot Client**: Библиотека `Telegram.Bot` (v22.9.2), режим long-polling в `TelegramBotPollingWorker`.
* **MAX Bot Client**: Кастомный HTTP-клиент `MaxCommandService` с пулингом и обработкой Webhook/LongPolling событий через `MaxUpdate`.
* **База данных**: SQLite 3 через Entity Framework Core 10 (`app.db`), права доступа `0600` (чтение/запись только владельцу процесса).
* **Сетевой уровень**: Встроенный `RussianTrustedCertificateValidator` для безопасного взаимодействия с защищенными хостами Минцифры без отключения проверки TLS.

## 2. Модель безопасности и соответствие 152-ФЗ

### 2.1. Конвертное шифрование токенов (Envelope Encryption `enc:v2:`)
Хранение авторизационных токенов (`AccessToken`, `RefreshToken`) в базе данных осуществляется по схеме двухслойного конвертного шифрования:

1. **Master KEK (Key Encryption Key)**:
   * 256-битный ключ, получаемый из переменной окружения `MIRAGE_TOKEN_ENCRYPTION_KEY` или секции конфигурации `Security:MasterKey`.
   * При отсутствии явного 32-байтного Base64-ключа производится деривация через PBKDF2/SHA-256 с фиксированной криптографической солью проекта.
2. **DEK (Data Encryption Key)**:
   * Для каждой операции сохранения токена генерируется уникальный криптографически стойкий 256-битный ключ: `RandomNumberGenerator.GetBytes(32)`.
3. **Шифрование данных (AES-256-GCM)**:
   * Исходный токен шифруется сгенерированным DEK. Используется 96-битный (12 байт) уникальный вектор инициализации (IV) и формируется 128-битный (16 байт) тег аутентификации (Tag).
4. **Шифрование ключа данных (AES-256-GCM)**:
   * DEK шифруется с помощью Master KEK с собственным 96-битным IV и 128-битным тегом аутентификации.
5. **Формат сохранения в SQLite**:
   ```
   enc:v2:<Base64( kekIv[12] + kekTag[16] + encDek[32] + dekIv[12] + dekTag[16] + cipherText[N] )>
   ```
6. **Очистка оперативной памяти**:
   * Все массивы с открытыми ключами DEK гарантированно зануляются в блоках `finally` вызовом `CryptographicOperations.ZeroMemory(dek)` во избежание дампа секретов при сканировании памяти процесса.
7. **Миграция и обратная совместимость**:
   * Токены с устаревшим префиксом `enc:v1:` (прямой AES-GCM без DEK) расшифровываются штатно и автоматически переводятся в `enc:v2:` при очередном обновлении токена.

### 2.2. Соответствие 152-ФЗ «О персональных данных»

| Требование 152-ФЗ | Реализация в ботах MirageDiary |
|---|---|
| **Согласие законных представителей (ст. 9 ч. 6)** | Обязательный экран онбординга при первом старте бота. Содержит прямое указание на согласие родителей/представителей для несовершеннолетних пользователей. До нажатия кнопки `✅ Согласен с политикой (152-ФЗ)` доступ к функционалу блокируется. |
| **Аудит волеизъявления** | В сущности `UserEntity` фиксируются поля `HasAcceptedPrivacyPolicy = true` и точный таймштамп `PrivacyPolicyAcceptedAtUtc = DateTime.UtcNow`. |
| **Право на отзыв и забвение (ст. 14, 21)** | Команда `/delete_account` и кнопка `cmd_delete_account` запускают процедуру полного удаления: отзыв OAuth-токенов в ЕСИА, удаление записи из `Users`, очистка кэша оценок и расписания. |
| **Локализация баз данных (ст. 18 ч. 5)** | Все базы данных, сессии и серверные узлы физически расположены на серверах в Российской Федерации. |
| **Несохранение аутентификационных данных** | Пароли пользователей от портала Госуслуг не вводятся и не проходят через бот. Авторизация делегирована мобильному шлюзу ЕСИА (OAuth2 PKCE S256). |

## 3. Архитектура экранов и UX

### 3.1. Концепция единого экрана (In-Place Editing)
Для предотвращения спама в чате бот не плодит новые сообщения при навигации:
* Все экраны (Расписание, Домашка, Оценки, Калькулятор, Настройки, Будильник, Профиль) обновляются через `SafeEditTextOrCaptionAsync` / `SendOrEditBannerScreenAsync`.
* Если сообщение содержит медиа-баннер, вызывается `EditMessageCaptionAsync`. Если текст — `EditMessageTextAsync`.
* Отправка нового сообщения происходит только при прямом вызове пользователем текстовой слэш-команды в чате.

### 3.2. Компоновка главного меню
Главное меню оптимизировано для отображения на экранах мобильных устройств без переноса строк и скроллинга:

```
┌────────────────────────────────────────────────────────┐
│ [Баннер: banner_menu.png]                              │
│                                                        │
│ 🎓 8Б • МАОУ СОШ № 113                                 │
├──────────────────────────┬─────────────────────────────┤
│ [ 📅 Расписание ]        │ [ 📚 Домашка ]              │
├──────────────────────────┼─────────────────────────────┤
│ [ 📊 Оценки ]            │ [ 🎯 Калькулятор ]          │
├──────────────────────────┼─────────────────────────────┤
│ [ 👤 Профиль ]           │ [ ⚙️ Настройки ]            │
├──────────────────────────┴─────────────────────────────┤
│ [ 🔔 До звонка ]   /   [ 🔔 До звонка ] [ 👑 Админ ]    │
└────────────────────────────────────────────────────────┘
```

* **Строка 1 (Повседневные операции)**: `[ 📅 Расписание ]` и `[ 📚 Домашка ]`.
* **Строка 2 (Учебная аналитика)**: `[ 📊 Оценки ]` и `[ 🎯 Калькулятор ]`.
* **Строка 3 (Профиль и настройки)**: `[ 👤 Профиль ]` и `[ ⚙️ Настройки ]`.
* **Строка 4 (Статус уроков и админка)**: `[ 🔔 До звонка ]` (для обычных пользователей) или парная строка `[ 🔔 До звонка ]` + `[ 👑 Админ-панель ]` (для администраторов).
* **Для неавторизованных**: Первая строка заменяется на кнопку `[ 🔐 Войти через Госуслуги ]` (открывает MiniApp для OAuth-авторизации).

### 3.3. Динамический компактный заголовок
Вместо шаблонного текста «Выберите действие:», заголовок меню динамически сообщает контекст:
* Для авторизованного ученика: `🎓 *{user.ClassName}* • {user.OrgName}` (например, `🎓 *8Б* • МАОУ СОШ № 113`).
* Для завуча: `🏫 *Завуч* • {user.OrgName}` с подсказкой о возможности отправки фото/PDF расписания.
* Для администратора: `👑 *Администратор* • Mirage Diary`.
* При проведении работ: автоматически добавляется строка `🔧 _Идут технические работы_`.

## 5. Подсистема «Умный будильник» (SmartAlarmService)

Фоновый воркер производит периодический мониторинг времени пользователей с учетом их индивидуального часового пояса (`UtcOffsetHours`, по умолчанию +5:00 Екатеринбург).

```
          ┌───────────────────────────────────┐
          │  SmartAlarmWorker (Каждые 60 сек) │
          └─────────────────┬─────────────────┘
                            │
       ┌────────────────────┼────────────────────┐
       ▼                    ▼                    ▼
   [ 07:30 ]            [ 17:00 ]            [ 20:30 ]
Утреннее расписание    Напоминание о ДЗ    Контроль инвентаря
и первый урок          на завтра           и сбор рюкзака
```

### 5.1. Триггеры и расписание

1. **07:30 — Утреннее расписание**:
   * Извлекает расписание на текущий календарный день.
   * Указывает время начала первого урока, номер кабинета и список предметов.
   * Фиксация: поле `LastScheduleReminderDate = "yyyy-MM-dd"`.
2. **17:00 — Домашнее задание**:
   * Проверяет невыполненные домашние задания на следующий учебный день.
   * Группирует по предметам с текстом заданий и прикрепленными файлами.
   * Фиксация: поле `LastHomeworkReminderDate = "yyyy-MM-dd"`.
3. **20:30 — Контроль рюкзака и специнвентаря**:
   * Анализирует предметы на завтрашний день через правилоемкий синтаксический анализатор.
   * Фиксация: поле `LastEquipmentReminderDate = "yyyy-MM-dd"`.

### 5.2. Правила парсера специнвентаря

Парсер нормализует наименования уроков (lowercase, trim) и сопоставляет их со словарем спецснаряжения:

| Предмет (паттерн) | Рекомендуемый инвентарь |
|---|---|
| `физ-ра`, `физкультура`, `спорт` | Спортивная форма, кроссовки для зала (зимой: лыжи и лыжные ботинки) |
| `изо`, `рисование`, `искусство` | Альбом, акварель/гуашь, кисти, баночка-непроливайка |
| `технология`, `труд` | Рабочая форма/фартук, материалы для практических работ |
| `геометрия`, `черчение` | Циркуль, транспортир, линейка, карандаши |
| `музыка` | Тетрадь для нот, учебник |
| `химия`, `биология` (лаб. дни) | Халат, тетрадь для лабораторных работ |

## 6. Кроссплатформенное связывание (Telegram ⟷ MAX)

Боты поддерживают объединение учетных записей Telegram и MAX Messenger для сохранения единого профиля, токенов доступа и настроек:

```
[Пользователь в Telegram]                    [Пользователь в MAX]
           │                                          │
    /settings -> [🔗 Связать с MAX]                   │
           │                                          │
    Генерация 6-значного кода                         │
    (например, "849201", TTL: 10 мин)                  │
           │                                          │
           └───────── Сообщает код в MAX ─────────────┤
                                                      │
                                            Ввод кода в чат: "849201"
                                                      │
                                                      ▼
                                       ┌──────────────────────────────┐
                                       │ Слияние профилей в SQLite    │
                                       │ • Копирование AccessToken    │
                                       │ • Синхронизация Class/Org    │
                                       │ • Объединение настроек Alarm │
                                       └──────────────────────────────┘
```

1. В исходном боте вызывается `cmd_link_account`. Сервис генерирует случайный 6-значный код через `RandomNumberGenerator.GetInt32(100000, 999999)`.
2. Код сохраняется в кэше `AccountLinkingService` с временем жизни 10 минут, ассоциируясь с `chatIdStr`.
3. На второй платформе пользователь отправляет полученный код текстовым сообщением.
4. Сервер сопоставляет код, копирует зашифрованные токены `AccessToken`, `RefreshToken`, `StudentId`, связывает настройки уведомлений и активирует доступ на обеих платформах.

## 7. Расписание звонков и статус уроков (BellScheduleService)

Для МАОУ СОШ № 113 реализован расчет текущего статуса уроков с учетом смен:

### Сетка звонков:
* **1 смена**:
  * 1 урок: 08:00 – 08:40 (перемена 10 мин)
  * 2 урок: 08:50 – 09:30 (перемена 15 мин)
  * 3 урок: 09:45 – 10:25 (перемена 20 мин)
  * 4 урок: 10:45 – 11:25 (перемена 15 мин)
  * 5 урок: 11:40 – 12:20 (перемена 10 мин)
  * 6 урок: 12:30 – 13:10 (перемена 10 мин)
  * 7 урок: 13:20 – 14:00
* **2 смена**:
  * 1 урок: 14:15 – 14:55 (перемена 10 мин)
  * 2 урок: 15:05 – 15:45 (перемена 15 мин)
  * 3 урок: 16:00 – 16:40 (перемена 15 мин)
  * 4 урок: 16:55 – 17:35 (перемена 10 мин)
  * 5 урок: 17:45 – 18:25 (перемена 10 мин)
  * 6 урок: 18:35 – 19:15

Алгоритм вычисляет:
1. Идет ли сейчас урок: `Урок N. До конца урока осталось: M мин.`
2. Идет ли перемена: `Перемена перед N уроком. До звонка на урок: M мин.`
3. Уроки завершены / еще не начались.

## 8. Регламент эксплуатации, сборки и деплоя

### 8.1. Сборка и обфускация

Проект защищен обфускатором **Obfuscar** для предотвращения реверс-инжиниринга серверных бинарников:

```powershell
# 1. Публикация Release сборки
dotnet publish .\MirageDiary.Server\MirageDiary.Server.csproj -c Release -r linux-x64 --no-self-contained -o .\publish\

# 2. Применение обфускации
& "$env:USERPROFILE\.nuget\packages\obfuscar\2.2.44\tools\Obfuscar.Console.exe" .\obfuscar.xml
```

> **Важно**: В `obfuscar.xml` настроены исключения (`SkipType`) для DTO моделей, контроллеров (`AdminController`, `MiniAppController`, `DiaryProxyController`) и сущностей EF Core, чтобы сохранить работоспособность сериализации `System.Text.Json` и рефлексии ASP.NET Core.

### 8.3. Верификация работоспособности

Для комплексной проверки продакшн-сервера запускается скрипт тестирования:
```powershell
.\test-all.ps1 -OnlyRemote
```

Тестовый набор автоматически проверяет:
1. `GET /api/health` — доступность REST API и состояние Kestrel.
2. `GET /privacy.html` — корректность отдачи статики и политики 152-ФЗ.
3. `POST /api/admin/login` — работоспособность аутентификации администратора после обфускации.
4. `GET /api/admin/stats` — целостность связи с базой данных SQLite.
5. `GET /api/admin/system/status` — системные метрики сервера.
